# Focused agent security

All government records and payments in this entry point are synthetic. It makes no real financial transaction. The model can select a bounded intent; it cannot supply user identity, roles, scopes, consent, workload credentials, amounts or execution authority.

`AGENT_AUTH=keycloak` reuses `packages/backend-kit/src/jwt.ts`: RS256 signature, issuer, audience, expiry, configured scopes and configured introspection checks. The principal is reduced to subject, configured workload, granted fines scopes and expiry. Execution re-authenticates using the current request's token. Configure existing online introspection for revocation; no token exchange or new identity provider is implemented here. This fines path has not been qualified against a real Keycloak realm with the new scopes. Production delegation, tenant/account entitlements and multi-hop authority remain separate work.

The shared verifier checks token expiry both before remote key or introspection requests and again after those checks complete, so a token that expires while waiting is not returned as verified. Callers still need to enforce current authority when a later action executes.

For RS256, the verifier requires the selected RSA signing key to have a modulus of at least 2,048 bits, as required by [RFC 7518 section 3.3](https://www.rfc-editor.org/rfc/rfc7518#section-3.3). A weak key does not make another eligible key in the same key set unusable.

Focused payment and renewal responses retain only known write-failure codes. Unrecognized tool errors are replaced with a fixed unknown-outcome code before replies and checkpoints are saved; the operation remains unresolved until reconciled. This is not a substitute for controlling credentials or sensitive data in tool inputs, outputs and logs.

The shared compatibility service-token client refuses redirects from its configured token endpoint. Client credentials are sent only to that configured endpoint, subject to its existing production HTTPS requirement; production egress restrictions and credential rotation remain separate controls.

The service-token client reads at most 64 KiB of a successful token response and requires a nonempty visible-ASCII token of at most 16,384 characters and an integer lifetime from one second through one day. Invalid responses are not cached, and response contents are not included in its errors. Body cancellation is best effort and is not awaited when a response is oversized or rejected.

Invalidating its local cache also fences any in-flight token request: its eventual result is rejected instead of being returned or cached, and subsequent callers coalesce around a new request. This does not revoke a token already returned to a caller or provide identity-provider revocation.

The shared browser OIDC client and generated Flutter web bridge refuse redirects during authorization-code and refresh exchanges, so those requests are not forwarded to a redirect destination. The retained compatibility shells still store tokens in session storage; moving them to a server-side session remains separate work.

Browser login callback state is consumed once, stripped from the address bar, and accepted only with a complete request for the current redirect URI created within the previous five minutes. Corrupt or future-dated requests are rejected before exchange. This browser-side state is not the server-side state and nonce required for production sessions.

The browser client rejects empty, oversized or non-printable token values and nonpositive, fractional or unsafe token lifetimes. A rejected refresh clears the expired session if it has not been replaced. This validates response shape, not token signatures or subject continuity.

Browser token exchanges count streamed response bytes and reject responses over 64 KiB, even when the sender misstates the content length. Malformed response contents are not included in the resulting error. This bound does not replace production identity or network controls.

Within one loaded browser client module, sign-out invalidates pending login and refresh results and clears pending PKCE state. A response cannot replace or clear a different session written while it was in flight, and instances sharing the same session and configuration coalesce refresh. This does not coordinate separate tabs or separately loaded modules, revoke a token already handed to a caller, or verify refreshed-token subject continuity.

`AGENT_AUTH=test` is a deliberately isolated opaque-token allowlist, loaded from private environment configuration. No missing token, default user or inferred scope is accepted. Unknown/expired identities fail closed; test authentication and fixture planning are refused in `NODE_ENV=production`. The server supplies the workload identity; the client cannot submit a principal. The internal REST simulator also requires the configured workload key, verified user scope and matching consent. This shared test secret is not a production workload attestation scheme.

SQLite owns thread subject/workload binding, expiry, exact action consent and original operation identity. Cross-owner access returns not found. Graph checkpoints have no credentials. Headers remain in request-local context and are reloaded on resume; raw provider errors never become persisted state, API errors or logs. Conversation input rejects recognizable credential patterns, but arbitrary user-entered secrets cannot be reliably detected: users must not paste secrets into chat. Private files, model endpoint configuration and the database must be protected by deployment filesystem permissions.

The React, Angular and Flutter fines routes keep each user access token in memory and only the conversation ID in session storage. The shared React and Angular focused client refuses to dispatch an already-cancelled request and discards late creation, inspection, progress and action results after cancellation; a dispatched action can still finish on the server and must be inspected or recovered. Every restore reauthenticates and checks ownership. The model key is never sent to the browser. Explicit OpenRouter configuration reuses the server environment key only at the official HTTPS endpoint, requires free model names and zero-price provider routing, refuses redirects and returns safe failures without fallback. Explicit LiteLLM selection reuses only the LiteLLM environment key at its matching configured endpoint; remote endpoints require HTTPS. The isolated compatibility stack sends LiteLLM TLS through the existing fixed-destination edge relay. Core verifies the configured upstream hostname and certificate, forwards only model headers, and bounds the response and deadline. The relay never terminates TLS, stores a model key, publishes its model port or accepts a client-selected destination. Direct backend egress stays blocked. Both text paths retain input minimization and strict action/approval checks. User-selected hosted inference sends minimized conversation text to that provider; the default fixture/local modes do not do so.

Payment requires an exact server-created quote and a matching, unexpired approval ID. A textual yes is insufficient. The execute node revalidates current authority, scope and consent. The simulator independently rechecks authority and consent, reloads current fine versions/amounts and rejects stale quotes. No model-selected field overrides those checks. Consent is specific to subject, workload, operation key and exact quote; expiry is checked again at the business boundary.

The focused client assigns a fresh, non-secret nonce to each simulator payment or renewal request. A conflict response echoes that nonce without returning the operation key, and the client accepts an allowlisted refusal only when its nonce matches the current request and the error envelope is otherwise exact. Missing, malformed, stale or mismatched nonces leave the outcome unknown and preserve the original recovery fence. This correlation does not authenticate a remote provider.

The payment key binds subject, operation version and sorted fine IDs/amount/versions. The simulator commits all fine effects and the receipt atomically. Concurrent/repeated requests cannot generate a second payment for already paid fines. A timeout after dispatch is an unknown outcome, not a failed payment: new actions are blocked until inspection/reconciliation using the same key. Recovery never invents replacement authority or an idempotency key. Expired unknown operations require operator resolution rather than silently extending consent.

Parsed JSON request bodies in the focused server and shared application reader require valid UTF-8. Invalid sequences are rejected before action dispatch; valid multibyte text remains supported across network chunks.

The focused HTTP server admits at most eight concurrent public requests per authenticated resident in this process, in addition to its global public limit. Trusted simulator calls use their separate reserved pool, and a public slot remains held until its handler finishes even after the client disconnects. A local HTTP regression also checks that repeated incomplete uploads release the resident slot without dispatch. Authentication itself is still protected only by the global admission limit; these limits are not distributed quotas and the regression is not extended load qualification.

The application runs as a single process against a local SQLite file. It limits concurrent graph transitions and rejects overlaps on a thread; it does not claim cross-process locking, replicated availability, immutable auditing, production tenant isolation or zero-loss host recovery. Use one replica and a persistent volume. TLS, identity provisioning, live model evaluation, container qualification and production release are outside the verified local slice.

The shared browser event-stream client cancels rejected, oversized or interrupted responses without waiting for the sender to acknowledge cancellation. Its frame limit applies to individual events and incomplete lines, allowing multiple small events to arrive in a single network chunk. React and Angular provide the expected session to the client, which validates each envelope and skips malformed or foreign events while advancing their replay cursor. Closing while token acquisition is pending stops the stream immediately; a later token result cannot start a request. The underlying token operation may still finish. Browser replay cursors are limited to 128 header-safe ASCII characters; invalid IDs clear the cursor after the event is handled or skipped, so the next connection requests a fresh snapshot. If a handler fails, the last successfully handled cursor is retained. A focused action whose stream fails remains unconfirmed and is not automatically retried; the resident must inspect or recover the original conversation.

The compatibility gateway admits at most five streams per session, 20 per authenticated resident and 1,000 per process. Slots are reserved before the asynchronous event subscription and released on closure, including when subscription completes after disconnect. These limits are process-local, not coordinated across replicas.

The gateway applies token expiry and its five-minute connection limit during subscription and replay as well as live delivery. If authentication expires before streaming begins, setup receives a 401; delayed delivery checks the deadline again before writing an event.

Within each compatibility gateway process, Redis subscription changes are ordered so concurrent listeners wait for connection and unsubscribe completes before a replacement subscribes. Closing the store invalidates pending subscription work; a failed channel subscription can be retried.

For a cursor reconnect, the gateway subscribes before reading replay, buffers a bounded number of live events during replay and suppresses replay/live overlap by event ID. If the buffer overflows, the connection closes so the client can resume from its last handled event. Replay is delivered in order without filling the live delivery queue with the entire backlog.

Focused React and Angular conversation creation and inspection accept at most 4 MiB of streamed JSON, including restored history and the service panel. They count bytes instead of trusting response headers, reject invalid UTF-8 and request cancellation without waiting for an uncooperative sender. A malformed or oversized result is reported as unavailable for inspection.

The focused simulator and compatible planner bound JSON response size. On overflow, they request cancellation but do not wait for an uncooperative response stream to finish cancelling. A write remains unknown for original-operation recovery; a model failure releases its active concurrency slot.

Focused planning and compatibility chat use shared LiteLLM deployment validation, bounded messages and per-owner model budgets. Identifiers are scrubbed before transport. Focused planning withholds assistant amounts and binds selected fine IDs server-side outside provider input. Neither planner receives the end-user token or supplies business authority. The quotas are process-local.
