# Automation worker

A local, off-by-default worker (`services/automation-worker`) that drives one leased job at a time through the authority path built under AUTO-03: prepare the execution, obtain its one credential from the broker, and present it to the dedicated execution route. It holds no authority of its own. Jobs are enqueued by the scheduler below, or by hand in tests.

## Enabling it

The worker refuses to start unless `AUTOMATION_WORKER_ENABLED=true`, never runs when `NODE_ENV=production`, and needs `AUTOMATION_RUN_ID` (an isolated payments run), the `automation-worker` client secret (`AUTOMATION_WORKER_CLIENT_SECRET` or `AUTOMATION_WORKER_CLIENT_SECRET_FILE`) and the provider and broker URLs. There is no Compose service. `npm run demo:verify:automation-execution` shows it against the real stack.

## Jobs

One job is one rule version, occurrence and target: the id is a hash of `(mandateId, policyVersion, occurrenceKey, target)`, so enqueueing again, or from another process, returns the same job, and a revised rule is a different job. The preparation request key is derived from the job id, so every retry is the same preparation.

At startup the worker atomically binds an empty jobs database to the configured run before the scheduler or worker can use it. Later startups must name that same run, including when scheduling is disabled. Use a separate database for each isolated run. An older database containing jobs, notices or threshold history without this binding is refused: its full scheduling history cannot be attributed safely from the database alone. Preserve it for inspection and reconciliation; do not copy its jobs into a fresh store or assume that an unrecorded occurrence is safe to repeat.

States: `QUEUED → PREPARING → PREPARED → CREDENTIALING → EXECUTING`, then `SETTLED`, `SKIPPED`, `FAILED` or `HELD`. `HELD` means the outcome is unknown or needs a person (an unknown capture, a lost credential); the worker does not touch it again. The one exception is a card challenge, held with reason `REQUIRES_ACTION`: the worker parks it for a wait and polls the owner's answer (see Needs the owner below).

## Leases and fencing

Contradictory automation responses, including refusals that carry credential or payment evidence and successful replies with a failure code, leave the original job held for inspection. Scheduling and preparation-inspection reads also reject a success response that contains an error code, without changing scheduling history. The scheduler validates the complete rule list first, including a threshold below its target and a reload no larger than that target; inconsistent rules cannot create jobs or change threshold history. It also rejects unknown rule or trigger fields and policy versions outside the mandate contract; adding fields requires updating both sides of that scheduling contract. Credentials are not persisted.

On SIGTERM or SIGINT, the worker finishes an already-claimed job, skips new claims even if a scheduler or authority read was in progress, and wakes promptly from an idle poll. A scheduler tick already in progress may still enqueue work for a later start.

`claim` hands out the oldest runnable job under a lease and raises the job's fence on every claim. Every renewal, attempt record and state change must present the fence while the lease is live, so a worker whose lease lapsed, or that lost a race, is rejected and simply stops. Two workers on one database file never run the same job. The step in flight when a lease is taken over is idempotent at the provider (the permit is consumed once and an admitted execution only resumes).

Claiming also checks the mandate and occurrence across all saved versions and targets in the same transaction. It skips other unclaimed duplicates with `DUPLICATE_OCCURRENCE`, even when they were inserted without the scheduler. If another version was already claimed, held or completed, a new unclaimed duplicate is skipped; already claimed work remains under its original identity. Skipping a duplicate does not prevent the surviving original from being claimed later.

## Persisted before dispatched

The state and an append-only attempt row are written before the step they describe. Steps carry these rules:

- **Prepare** records the configured run before dispatch and retries under the original request key. If attempts are exhausted, or a later refusal follows a lost or interrupted response, the job is held as `PREPARATION_UNKNOWN`: the provider may have reserved the original occurrence. A worker configured for a different run cannot retry or request a credential. Older in-flight jobs with an uncertain preparation and no saved run are held rather than rebound. No credential is requested until that preparation is reconciled.
- **Inspect preparation** with the exact worker identity using `GET /internal/automation-runs/{runId}/requests/{requestKey}`, or `HttpExecutionGateway.inspectPreparation` with the original job's rule, occurrence, version and request key. The read returns a recorded preparation or skip without making a new reservation. A missing record does not prove an earlier in-flight request cannot still commit; inspection alone never releases the held job or requests a credential.

For a local held job, set `AUTOMATION_JOBS_DB` to the existing jobs database, `AUTOMATION_RUN_ID` to the original run, and the worker client secret through `AUTOMATION_WORKER_CLIENT_SECRET` or `AUTOMATION_WORKER_CLIENT_SECRET_FILE`. Run `npm run automation:inspect-preparation -- <job-id>`. The command opens the jobs database read-only, derives the original request key and prints `PREPARED`, `SKIPPED` or `NOT_RECORDED`; it does not start the worker, request an execution credential, change history or release the job. Skip reasons are not printed. Older jobs held before run binding may not contain a run ID, so the operator must supply the original run: the command cannot independently prove that choice in that case. `NOT_RECORDED` is inconclusive while an earlier request might still commit.
- **Credential** is requested once per job. A definitive refusal fails the job. A transient failure is retried only because a retry can only replay or be refused. An already-issued credential, or an outage that exhausts the retries, holds the job.
- **Execute** retries only the same credential while it is alive. A provider rejection before funds fails the job (the provider has released the reservation); a captured-but-unsettled order, a challenge or a lost response holds it.
- **Restart** while a credential was in flight or in use holds the job (`CREDENTIAL_LOST_AFTER_RESTART`). The credential is never written to the database, the outbox, the attempt log or the logs, so it cannot be recovered, and a fresh one is never requested.

## Scheduling

`Scheduler.tick(now)` (`scheduler.ts`) turns approved rules, the clock and the calendar calculator in `packages/protocol-core/src/mandate-schedule.ts` into jobs. It reads the rules from the worker-scoped view of the run (`GET /internal/automation-runs/{runId}/rules`, plus `/rules/{mandateId}/invoices` and `/balance`), which only the `automation-worker` identity may call and which reserves nothing.

The HTTP scheduling reader limits each response to 64 KiB and requires an explicit, unambiguous success envelope. Threshold readings must contain nonnegative safe integers for both balance in fils and the qualifying debit count; a malformed or oversized reading does not re-arm or fire that threshold. An oversized rule list requires reducing the local run's data before scheduling can continue.

The reader validates the entire rule list before processing it: identities must be unique and usable, state and trigger fields must be recognized, trigger values must fit the mandate contract, and the time zone and ordered time window must be valid. Invalid rules leave that tick's scheduler history untouched.

Invoice lists must contain real calendar dates, fine lists must contain unique bounded identifiers, and parking sessions must have a usable ticket, status and expiry. The reader validates the entire returned list before the scheduler records any occurrence from that reading; invalid data is retried on a later tick rather than partially scheduled.

- A rule schedules only while it is approved and inside its start and expiry window; time never revives consent.
- Calendar rules produce one occurrence per local month (`CAL:YYYY-MM`) with the rule's `LAST_DAY` or `SKIP` month-end behaviour in its own time zone. Invoice-due rules produce one occurrence per due date (`INV:YYYY-MM-DD`) three local days, or the rule's `daysBefore`, ahead at 09:00. An invoice occurrence is eligible only from the mandate's start, inclusive, until its expiry, exclusive; catch-up and previews use the same window.
- `tick` is a function of the rules, the occurrence keys already recorded for the rule under any version, and `now`. Repeating it, running it from two processes or advancing time in small or large steps gives the same jobs, and a revised rule never repeats an occurrence an earlier version handled.
- After downtime only the latest missed periodic occurrence stays pending, including when older jobs were queued before the interruption. Older unclaimed jobs are atomically recorded as final `SKIPPED` jobs with reason `MISSED_CATCH_UP`. Claimed, in-flight or held work is never replaced: newly due periodic occurrences are skipped with `PRIOR_UNRESOLVED` until that work is resolved. This avoids a burst and keeps every skip visible.
- If older data contains multiple unclaimed jobs for the same periodic occurrence under different rule versions, catch-up keeps at most one and records the rest as `DUPLICATE_OCCURRENCE`. If the occurrence already has a completed record, all unclaimed duplicates are skipped. The provider still rechecks the retained job's original rule version before admission.
- A balance threshold (`LOW_BALANCE`) fires one job per dip. Firing, the sequence number (`THR:n`) and the job are one transaction. The trigger stays disarmed while the balance stays below the threshold and re-arms when it recovers, and it fires again only after a new qualifying external debit: a payment from the wallet counts, while the reload's own credit, a top-up and a refund of a reload do not, so the reload cannot loop on itself (see Wallet reloads).
- Event-driven triggers (new fine, parking ending) schedule nothing here.

The loop runs the scheduler only when `AUTOMATION_SCHEDULE_ENABLED=true` in addition to `AUTOMATION_WORKER_ENABLED`; both are off by default. The business clock stays separate from security time: the scheduler takes `now` as a parameter, so a simulator clock can drive it without touching token expiry.

## Wallet reloads

A `WALLET_RELOAD` rule keeps a wallet funded from an approved card. When the balance is below the rule's threshold, preparation computes one finite amount (the rule's reload amount, never past its target balance, at least AED 1 and at most the funding limit, within the per-payment cap and the period and lifetime budget), reserves it and creates the gateway's funding order for that card inside the same transaction. The order is marked automatic: the ordinary approve, execute, challenge and cancel routes refuse it, and only the dedicated execution route admits it, with the same one-time permit, freshness check and release rules as a bill payment.

Capture and wallet credit share one local transaction, so there is no provider chain. Only one funding order can be open for a wallet at a time, so two threshold events cannot open two reloads; a second occurrence is refused while one is active. At admission the rule must still be approved and the balance must still be below the threshold for the same amount, so an owner top-up or a revoked rule stops it. A decline fails the job as requiring action, a challenge holds it, and neither is retried or switched to another source; because the trigger stays disarmed until the balance recovers, a card that keeps failing is not charged repeatedly.

## Toll and prepaid recharges

A `RECHARGE` rule keeps one toll tag or prepaid number topped up. The scheduler reads the balance of exactly that target at its own provider and fires when it is below the rule's threshold; the only event that can fire it again is usage recorded on that same target (a recharge, a refund or usage on another line, tag or provider cannot). Preparation checks the target is active, the approved amount is still one of its denominations and would not carry the balance past the rule's target, then asks the source provider for a recharge quote and reserves it with an automatic payment order that only the dedicated execution route can admit, exactly like a bill. The quote is the payable: if the balance moves before admission (more usage, or the owner recharging by hand) it no longer matches, admission refuses it and the reservation is released.

Cost, count and cooldown caps are shared with every other rule, and a rule has at most one unfinished recharge, so two low-balance events cannot open two. Funding is the rule's own wallet or approved card and nothing else: short funds or a decline fail the job as requiring action and charge nothing, and no job starts another, so a failed recharge never causes a wallet reload or any other charge (chains of one automatic payment funding another stay off).

## Fines

Automatic fine payment is a separate, opt-in rule (`FINE_PAYMENT`): the owner approves one plate, a finite list of fine types, a per-fine amount cap and period and lifetime counts. Without such a rule fines stay manual. Every unpaid fine of the plate is its own occurrence (`FINE:<fine id>`), announced once by the scheduler however many times it looks; paid fines are never announced again.

Each occurrence is judged on the fine's current record at preparation, not on the event that announced it. A fine that is paid or withdrawn, a type the owner did not approve, a simulated restriction on the fine (`paymentRestricted`) and an amount above the cap are all skipped with a reason (`FINE_NOT_PAYABLE`, `FINE_TYPE_NOT_APPROVED`, `FINE_REQUIRES_REVIEW`, `OVER_PER_PAYMENT_CAP`), move nothing, reserve nothing, and are recorded as requiring action so the owner can decide. A discount applied before preparation is honoured, so the rule pays the current amount. Once a fine is reserved by an execution the source provider refuses to amend or restrict it, and admission re-reads the record anyway.

An automatic and a manual payment of one fine cannot both proceed: a manual review that already holds the fine makes preparation refuse it, a prepared execution makes a manual review of the same fine refuse, and either way the fine settles once with one debit. Fines that arrive together are paid one at a time: a mandate's cooldown between preparations is a wait (the job is retried after it under the same identity), not a failure, and the period and lifetime counts still bound the total.

## Parking extensions

A `PARKING_EXTENSION` rule binds one session (ticket, plate and zone) with a maximum number of hours, an end time and the usual cost, count and cooldown caps. When the session is within the rule's minutes of ending, the scheduler announces one occurrence per session expiry (`PARK:<ticket>:<expiry>`); extending moves the expiry, so the next extension is a new occurrence and not a repeat. Everything is judged on the current session at preparation:

The next-run preview uses the later of the mandate's start and the session's ending-window opening. That instant must precede both the mandate expiry and the session expiry; the session itself may end after the mandate expires.

- the session must exist, be running and unexpired, and match the bound plate and zone; a departed session (`SESSION_ENDED`), an expired one (`SESSION_EXPIRED`, never revived), a missing one (`SESSION_NOT_FOUND`) or another plate or zone (`SESSION_MISMATCH`) is skipped, so a session is never created or inferred;
- one more hour must stay within the rule's maximum hours (`MAXIMUM_DURATION_REACHED`) and end time (`END_TIME_REACHED`), which bounds any overnight stay; those two ask the owner to decide;
- the hour is priced by the zone's tariff and must fit the per-payment cap.

The source provider issues a quote for exactly that session state, and the extension is paid by an automatic order that only the dedicated execution route can admit, like any other payment. The order is bound to the session instead of a linked biller, and a manual order cannot take such a quote. The session only grows when an admitted, captured and settled order applies the quote while the session is exactly as quoted: departure, expiry or any other change after preparation makes the quote stale, admission refuses it, and nothing is charged. A rule has one unfinished extension at a time, an extension cannot be refunded, and the legacy manual extension still needs its own proof of payment.

## Subscription renewals

A `SUBSCRIPTION_RENEWAL` rule renews one billing period at a time (`CAL:YYYY-MM`). `renewalEligibility` (`packages/protocol-core/src/automation-eligibility.ts`) allows it only for an active subscription, from the one unpaid invoice issued for exactly that period, at exactly the current plan price and inside the cap. A plan change or repricing (`TARIFF_CHANGED`), a lapsed subscription, an uninvoiced or ambiguous period and a restricted invoice are skipped with a reason and recorded as requiring action; an already-paid period is never paid again. The paid order carries the receipt. `automationEligibility` is a default-deny map from catalog capabilities to mandate operations: plan changes, tenancy and utility activation, rides, dining, parking activation and the rest stay review-required and inherit no financial mandate authority.

## What the owner is told

- **Before a run:** when a rule's next run is inside the lead time (24 hours by default), the scheduler records one `UPCOMING_RUN` notice per rule and occurrence in `job_notices` (a reminder, not a job; it moves nothing and a paused or expired rule announces nothing).
- **Needs the owner:** a declined card, a card over its limit, short wallet funds and similar failures end the job as `FAILED` and record a `REQUIRES_ACTION` outbox event. A card challenge holds the job (`HELD`, reason `REQUIRES_ACTION`) and records the same event, then the worker parks it for `challengeWaitMs` (60 seconds by default) and asks the broker once per wait for the owner's answer. While the answer is pending nothing is recorded and no credential exists. If the owner rejects it, the job fails with `CHALLENGE_REJECTED` and a `CHALLENGE_ANSWERED` event with `decision: REJECT`, and nothing else runs. If the owner approves it, the broker issues one resumed credential for the same execution and operation, the job records `CHALLENGE_ANSWERED` with `decision: APPROVE` as it moves to `EXECUTING`, and the same order is executed once more. A resume that cannot be confirmed (an unreachable broker, or a crash while the resumed credential is being requested) is held for reconciliation, and a refused resume holds with its reason; neither is asked again. The worker never tries another source, a lower amount or a different invoice for that occurrence, and the failed occurrence is not retried.
- **Review needed:** a skip that only the owner can resolve (an unapproved fine type, a restricted fine, an amount above the cap, a parking session at its maximum hours or end time) is recorded as `REQUIRES_ACTION`.
- **Everything else:** a skip, a settlement, a held unknown outcome or an ordinary failure records `SKIPPED`, `SETTLED`, `HELD` or `FAILED`.

Only recognized provider skip and order-failure codes are saved in job history. An unfamiliar skip is held as `PREPARATION_UNKNOWN` before a credential is requested; an unfamiliar order failure is held as `OUTCOME_UNKNOWN` for reconciliation. The provider's unrecognized text is not persisted.

The worker stores the prepared amount in integer fils with the job before requesting a credential. It reports settlement only when the matching order has a readable receipt for that exact amount in AED; missing or contradictory receipt evidence holds the original execution as `OUTCOME_UNKNOWN`. A prepared job from an older database without a stored amount is held as `PREPARATION_UNKNOWN` before requesting or resuming a credential.

An invoice is chosen at preparation: the earliest-due unpaid, unreserved invoice that is within the rule's per-payment cap. An invoice above the cap is skipped, never lowered, and does not hold up a smaller one behind it. Paid and withdrawn invoices are never offered. Wallet, card, DEWA, Etisalat and du invoices follow the same path.

## Outbox

`job_outbox` has at most one row per job and kind (`PREPARED`, `SKIPPED`, `SETTLED`, `FAILED`, `HELD`, `REQUIRES_ACTION`, `CHALLENGE_ANSWERED`), written in the same transaction as the state change. The owner inbox turns these into entries (`services/automation-worker/src/inbox.ts`).

The inbox is served by `GET /api/payments/automation-inbox` (`services/agent-core/src/automation-inbox.ts`) and shown in the React payments panel. The owned rule set comes from the provider's owner-scoped mandate list, so only the signed-in owner's entries are returned, and switching account re-reads them. The response carries the request's `requestId`; each entry's `id` is the source key the worker derived (`job:<job>:<kind>` or `notice:<rule>:<occurrence>:<kind>`), so polling never duplicates an entry. The feed is polled rather than streamed. The worker's job store is read per request and closed again, and a missing store is an empty inbox rather than a new file. A held card challenge entry names its order, and the panel answers it with the same order challenge action the payments list uses (approve pays once; reject closes the order with nothing paid). The answer is the owner's, through the signed-in session; the worker never answers.

Before opening the job store, the inbox validates the mandate-list envelope and each unique mandate ID, and checks that every record names the signed-in subject and selected account. A malformed or cross-owner list makes the inbox unavailable rather than exposing partial results or presenting a misleading empty feed.

## Kill switch and owner pause (AUTO-15)

The operator's global kill switch is a persisted flag in the worker's job store (`kill_switch`). Engaging it with `node --experimental-strip-types scripts/automation-kill-switch.ts engage --reason "<why>"` (release with `release`, check with `status`; `AUTOMATION_JOBS_DB` names the store, and a missing store is an error, never a new file) changes three things. No new job is claimed. A job that has finished a step stops before its next one, untouched, and carries on after release. A credential already issued while the switch engages is held as `KILL_SWITCH_ENGAGED` and is never presented or replayed; the provider's permit then expires unused and its reservation is released by the provider's own sweep. A restart keeps the switch engaged. The switch is also reachable from the application: `POST /api/payments/automation-kill-switch` with `engaged` and a `reason` (required to engage). Only a signed-in account listed in `AUTOMATION_OPERATOR_SUBS` may use it; anyone else is refused and nothing changes. That is an allowlisted operator sign-in. The broker also holds a desired state: the `automation-admin` client, whose only scope is `automation.admin`, writes it at `POST /api/delegation/automation/kill-switch`; the worker reads it through its own gateway with its execute scope, and no other caller reaches either direction. The worker applies a desired state only when it is newer than the worker's own last change, so a local engage or release is never undone by an older authority state. An unreadable or absent state changes nothing. The worker accepts only the documented switch response fields, so contradictory or unexpected data cannot release an engaged switch. The panel control for the admin route is still open, because the owner's session cannot carry the admin scope. The local script above still writes the worker's store directly, for whoever can write it.

The broker and worker stores advance their recorded change times even when the local clock repeats or moves backward. A worker records the authority's original time, including when the state is already the same, and applies it atomically only if it is newer than the current local state. This prevents a delayed poll from hiding a later authority change or overwriting a newer local override. Ordering changes from different hosts still depends on their clocks being sufficiently synchronized; the local demo does not prove distributed clock consistency.

The worker bounds the broker's switch response and requires a successful, well-formed state with a positive integer change time and a bounded reason. A contradictory, malformed, oversized or unavailable response leaves the current switch unchanged; a missing desired state also changes nothing.

The worker's preparation, credential and execution HTTP responses are bounded. Only documented refusal codes are retained, and provider error text is not used in worker errors or job history. Malformed, oversized, contradictory or unrecognized replies are uncertain: credential or execution uncertainty remains held under the original identity rather than being reported as a definitive refusal.

Success responses carrying an error and skips that also contain preparation facts are rejected as contradictory. A credential must be nonempty, bounded, free of whitespace and have more than five seconds of confirmed lifetime; the same checks apply to a resumed challenge. An unusable credential is held as uncertain and is never presented to the execution route.

The broker separately bounds its provider execution-view response and requires an unambiguous success envelope. Before issuing a permit, it validates the current, expired and skip flags as explicit booleans and checks the associated identities and versions. Malformed views issue neither a permit nor a credential.

Each automation permit is bound to the mandate's owner and membership eligibility version. When eligibility enforcement is enabled, the broker checks that version before and after minting, and again at provider admission and session use; revoking and restoring membership cannot revive the old authority. If eligibility changes after a token is minted, its fingerprint remains bound and no replacement token is issued. Older permits without an eligibility version cannot be used and require inspection. The legacy mandate version defaults to `1:1`, as in the provider's existing preparation check.

The execution response must name the prepared order, contain a recognized state and carry an explicit capture flag. A different order, missing flag, settled result without capture or with a failure code, or challenge after capture is held as an unknown outcome. These checks do not independently verify the payment amount or replace provider reconciliation.

Before requesting an execution credential, the HTTP adapter matches the preparation to the queued run, mandate, occurrence and policy version. It also checks the prepared state, identifiers, positive bounded fils amount and AED currency. Skipped preparations must name the same mandate and occurrence. Invalid responses do not issue a credential; preparation retries retain the original request identity. The amount check validates the preparation's shape and does not independently authenticate the provider's quote.

An owner's pause-all (`POST /api/payments/mandates/pause-all`, with `requestKey`) pauses each approved rule at its current version, under a key derived from the request and the rule. Unconfirmed or refused rules are reported individually; retrying with the same key does not repeat the pauses that succeeded. Pausing stops new runs only. It does not reverse a payment that was already committed.

Before dispatch, pause-all validates the complete owner-scoped list, including each rule's account, owner, state and version. It reports a rule as paused only when the response confirms the same owner and account, the same rule, the paused state and the next version. A lost or contradictory response is reported as `PAUSE_UNCONFIRMED`: the rule may already be paused, so inspect its current state rather than assuming failure. Other rules are still attempted, and provider-supplied error text is not exposed.

The React panel announces confirmed pauses separately from unconfirmed results and asks the owner to check current rule state before trying again. It also treats an unreadable result as unconfirmed rather than showing a false zero-paused success.

Signing out and pausing are different things. Signing out ends one browser session; it does not stop a rule, because a run is not tied to that session. A pause or a revoke takes effect where the run is admitted: the provider re-reads the rule, its source and its payable before any money moves, and a run that is no longer approved is closed with nothing moved. Pausing never reverses a payment that was already committed.
