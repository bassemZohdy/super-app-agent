## How to work this file

Agent rules are in [AGENTS.md](AGENTS.md).

- One bullet per task: scope that is **still open**, then `Done when`. A bullet stays under 700 characters (`npm run check:docs` enforces it). Design and history belong in the guide or the changelog, not here.
- Show partial work with indented sub-steps (`[x]` landed, `[ ]` open), never with prose. Delete a task here and add its changelog entry in the **same commit** that meets `Done when`.
- Work the [critical path](#critical-path) in order. Take something off it only when the critical path is blocked, and say why in the commit message.
- Documentation per slice: one changelog entry, plus the guide you changed. An evidence report is written per milestone, not per slice. Outside dated evidence reports, do not record test totals, task counts or percentages; they go stale. The one exception is the progress block below, which `npm run progress` regenerates from this file and the docs check verifies.
- Run the narrowest test while iterating (`node --experimental-strip-types --import ./scripts/test-env.ts --test services/test/<file>.ts`) and the full `npm run check` before pushing a checkpoint.
- Do not re-enable disabled GitHub workflows. Dependency advisories, native/device validation, external security approval and production HA are production-gate work.

## Critical path

The initial focused-agent path (`P2-16`, `P1-04`, `P1-05`) is delivered for the local demo. The compatibility acceptance path ends with `QA-06` (retained-shell journey parity), also delivered; production work remains separate.

Use one TypeScript/LangGraph.js agent with embedded SQLite and fixture-backed REST simulation. Default demo adoption does not require PostgreSQL, Redis, external Keycloak, a workflow engine, a gateway service or a UI-protocol migration. The test authority and fixture planner remain explicit demo adapters; production requirements are not silently waived.

The compatibility acceptance track (QA-05 to QA-10) is delivered. Preserve its work and the existing security and payment contracts, and keep the [shell parity guide](docs/development/shell-parity.md) in step when a shell gains or loses a journey. Do not mark production tasks complete merely because the focused slice passes.
