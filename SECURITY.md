# Security boundaries

This repository is a local demo. The reference stack uses known users/client secrets, local HTTP, single-node Redis and embedded SQLite. The named entities and all money are simulated. Do not deploy this realm/configuration publicly or use real personal/card/government records.

## Identity and service authorization

React and Angular use a public Keycloak client with authorization code and S256 PKCE, state/expiry checks, refresh and logout. Browser tokens live in sessionStorage, not in URLs or committed configuration. This remains readable by same-origin JavaScript: production needs an explicit XSS/session architecture and hardened deployment. Flutter's current sign-in is an explicitly local-demo password grant; native PKCE remains pending.

Core and application APIs verify RS256 signatures against configured JWKS, exact issuer/audience, finite bounded token times, access-token type and user subject. Integrated Compose also performs authenticated online introspection on each request. ID tokens and revoked/inactive access tokens are rejected. JWKS fetches are issuer-scoped, bounded, deduplicated and cooled down on unknown keys. Application APIs additionally require `superapp-user`. The core's `DEMO_AUTH=true` bypass applies only outside production and is disabled in integrated Compose. Fixture mode intentionally retains weaker legacy handlers and singleton data for offline tests.

Interactive application calls forward the signed user bearer; providers validate `provider-api`, `superapp-shell`, the user role and account ownership from JWT `sub`. With the reference delegation profile enabled, service credentials cannot impersonate humans through `X-User-Subject`. A separate narrowly scoped machine lane retrieves captured payment proofs. Older fixture tests retain their explicit compatibility profile. No service credential enters a browser; production provider/JWKS/token endpoints require HTTPS.

The separate trusted broker uses supported RFC 7523 and private-key client authentication, with separate local issuer/client keys mounted only into that service. Grants bind exact issuer, owner, actor, account, purpose, operation/body, expiry and limit; tokens are fingerprint-bound to grant version and operation. Providers check current authority without positive caching before executing. Revocation before the atomic authorization reservation denies; an already authorized effect may complete. No custom `act` mapper, scripts, native preview delegation or agent-held user refresh token is used. The broker refuses production-mode activation. [Decision and residual risks](docs/adr/ADR-0012-secure-delegation-demo.md) · [Runbook](docs/development/delegation.md).

Delegated writes are limited to one explicitly approved synthetic wallet credit of AED 1–10. Unknown execution blocks new work; no reset/retry bypass is provided. Demo SQLite audit is durable but not an immutable external audit system. General financial budgets, entitlement/unlink lifecycle, schedules, HA, KMS, rotation, sender constraints and independent security approval remain open. The common provider audience and local HTTP are demo boundaries, not a production deployment profile.

## Session ownership and recovery

Integrated mode stores owner subject, immutable selected account, up to 100 messages, current surface/revision and reconciliation state in Redis. Default inactivity TTL is one hour. Active requests renew an expiring lease, check it before mutations, and use token-fenced saves/releases. Overlaps return 409; Redis failures fail closed rather than creating new sessions. React can list/restore/delete only the signed-in user's conversations.

Redis also persists 100 replay events/session and carries cross-process pub/sub. Socket backpressure/listener bounds remain local to each core process. The reference AOF uses `everysec`: normal restarts preserve state, but a crash can lose recent writes. Global quotas, HA, encryption, retention enforcement and disaster recovery remain production work. Online revocation is checked for new requests/reconnects; existing streams remain bounded by expiry/maximum duration. Deleting an idle conversation deletes its state/events and active graph continuation; entity financial/business records are retained. Redis checkpoints share the session TTL; this is not a tested disaster-recovery or general workflow store.

## Business writes and payments

Every provider write requires a persisted per-account idempotency key and a request hash. Matching replays return the stored result; changed payloads conflict. Input schemas reject unknown fields and invalid amounts. Gateway amounts are integer AED fils; capture/decline/refund and balance updates are transactional. Refund is allowed once per captured payment.

Providers check captured payment ownership, merchant, reference, amount and refund state before settlement, and record consumed proof IDs. Application quotes derive from provider resources. Core stores an approval ID, five-minute expiry, subject/account/revision and canonical surface digest. Every advertised payload field must match; missing, extra, altered, expired and stale actions fail. Cancellation invalidates the pending approval and graph continuation. The conversation retains at most 50 approval lifecycle entries. This is a one-time demo proposal binding, not a cryptographic provider quote, delegated grant or immutable audit service.

Capture and entity settlement are separate transactions. An unknown outcome blocks further mutations in that conversation; no cross-service atomicity or automatic compensation is claimed. A provider refund does not itself reverse a settled entity bill. Operators must reconcile payment and entity state. Redis persistence cannot guarantee exactly-once external effects under all crashes or lease-loss scenarios.

## Models, data and secrets

The active demo uses local Qwen/llama.cpp text, KittenTTS speech and Whisper dictation. Inference services expose no host ports; authenticated core APIs use fixed local hosts, input/output/time/rate limits and allowlisted presets. Models and Python dependencies are pinned; explicit setup downloads allowlisted files and records hashes. Runtime loads local files, with speech download/telemetry disabled. There is no automatic cloud or browser speech fallback. Existing OpenRouter credentials remain private and are not forwarded by Compose; only the explicit historical diagnostic/helper can use them. Model-generated text cannot authorize service effects. See [local AI boundaries and licences](docs/development/local-ai.md).

Integration profiles omit real Emirates IDs, but prompts/surfaces still contain synthetic names, vehicle/premise references and bills. Production needs data minimization, approved provider egress/consent, redaction, retention/deletion controls and audit. Short microphone audio is processed in RAM by local inference and is not retained or logged. Dictation stays an editable draft until Send; submitted transcripts/replies use normal chat retention. The verifier alone writes synthetic fixtures and an original public sample. Browser cancellation stops capture/upload/playback; bounded server work may finish. Setup still needs image/dependency/model downloads and is not an air-gap or egress-firewall guarantee.

`.dockerignore` excludes `.env`, local databases and repository metadata. Generated OpenAPI examples contain no access tokens. The seeded realm and Compose secrets are intentionally public demo credentials and must be replaced outside local development.

HTTP readers enforce byte-based 64 KiB bodies, JSON media type, read deadlines and controlled malformed/aborted input handling. Each process has bounded IP rate/concurrency/cardinality budgets. These do not establish distributed user/tenant quotas. MCP uses the same identity/action guard, validates host/origin and caps input; it cannot bypass a current approval.

## Planned payment and automation boundary

The [payment/automation extension](docs/architecture/payment-automation-demo.md) now implements owned setup records and non-executable previews. Saved-card order execution and recurring automation remain planned. Current wallet effects use a balanced local journal, projection checks and consistent migration backups; these are application integrity controls, not administrator-resistant audit. [Journal boundaries](docs/development/payment-ledger.md). Setup uses strict fields, provider-verified links, signed owner checks, source versions and idempotent metadata updates; the preview digest is not an authorization credential. It requires owned synthetic method/biller records, authoritative quotes, unique payable reservations, finite versioned mandates, short-lived exact execution grants, conservative budget reservations and authenticated simulator controls. Raw card/bank credentials are outside demo scope. Payment capture, provider settlement and refund/reversal are distinct effects; timeout is an unknown outcome, not permission to retry a new charge. Revocation must stop new admissions with a documented boundary for already-admitted work. The existing small delegated-credit grant is not authority for recurring bills or general provider writes. AUTO-02 and QA-01 define the new review/tests without closing production requirements.

Payment-resource lifecycle locks are owner/version checked and bounded, and block source removal/archive in the same provider transaction. They are server-internal references, not authorization or consent proofs. Disabling a source stops new bindings without silently discarding in-flight work. The scenario CLI controls only its fixed isolated preview store using local operator access; it exposes no network control and never changes global/security time. Verified admin identity and exact execution/run binding remain SIM-05/AUTO requirements before any financial scenario control.

Provider payable revisions bind source-owned identity, amounts and lifecycle terms; they are not spend credentials. Trusted scenario issuance/amendment has no public route. Current-revision settlement rejects substituted account/currency/merchant/amount/proof, but cross-provider capture admission and refund/claim serialization remain PAY-07–PAY-10 requirements. Keep new stored-order and automatic execution disabled until their gates pass. [Payable boundaries](docs/development/payables.md).
